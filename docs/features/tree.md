# Digital tree (2D and 3D)

**Owner:** Role 2, Wei Jie

**Where the code is**

- backend/features/tree/routes.js
- frontend/tree/, frontend/3dTree/
- frontend/admin/js/tree.js (Digital Tree Adjustment tab), frontend/admin/js/tree3d.js (its 3D Tree Settings tab), backend/features/parameters/tree3d.js (3D settings defaults and checks), and the leaf / background / vip-leaf / treeParameters routes still inside backend/features/admin/routes.js

**What it does**

The wall display. /api/tree returns this year's visitors as leaves; tree.js places them around the trunk, animates falling leaves and VIP gold leaves, and polls for new feedback. The admin tab controls growth stage, backgrounds, leaf images and the title box. A new feedback's leaf first shows at the bottom middle of the wall for treeParameters.leafShowcaseSeconds (12 seconds by default, "Time at the Bottom Middle" in the 2D Visualization Parameters, one setting shared by both trees and also set from the 3D Tree Visualization Parameters, saved by PUT /api/admin/parameters/treeParameters too; 0 flies at once; an empty box saves the default, not 0), then flies to the tree; several new leaves take turns there. On the 3D tree new leaves arriving together are split into groups as the admin sets ("Split new leaves arriving together": into a number of groups, tree3dParameters.leafBatchCount, 3 by default, so 10 into 2 groups are 5 and 5; or into groups of up to leafBatchSize leaves; leafBatchMode), as evenly as they go, side by side at the bottom of the screen below the tree (spread evenly for its size, clear of the title box), then join the tree in no set order, each at its own moment (frontend/3dTree/feedback-leaves.js); /3dTree?demo=10 shows it without submitting anything. New feedback reaches both trees at once (event-driven refresh, Task 2): each open tree screen keeps one Server-Sent Events connection, GET /api/tree/events (backend/features/tree/liveEvents.js, wired in features/tree/routes.js; on both servers). While a screen is connected, its server checks the database every 2 seconds with one small query, however many screens are open (a fingerprint: the active feedback count, the newest feedback id and a checksum of the VIP names), and the settings file's time; when the fingerprint changes (a feedback or pledge saved, deleted or archived, a VIP added, removed or renamed) every screen is told "tree" and fetches its leaves at once, and when the admin saves settings, "settings". A feedback saved by the same server tells the screens straight away (nudgeTreeScreens in features/feedback/routes.js); one saved by the other server is found by the 2 second check, so it works whichever server the tablets use. Measured in Chrome: the new leaf on the 2D screen 0.1 s after a save on the same server and 1.6 s after one on the other server (before: up to 5 s), with no leaf downloads while nothing changes (before: every 5 seconds per screen). While connected, the timed check is only a safety net (every 2 minutes; the 3D settings every 30 seconds); if the connection drops, the browser reconnects by itself, the screen checks every 5 seconds meanwhile and fetches anything missed when it is back (2D: tree.js connectTreeLiveUpdates; 3D: frontend/3dTree/live-updates.js, shared by feedback-leaves.js and tree3d-settings.js; not on the admin's /tree-demo or in the 3D capture mode). The leaf count for the automatic growth stage is counted again as soon as a change is found. A leaf pushed off by a new one falls smoothly on both trees: it drifts out and flows down in one curve (no zigzag or spin), settling softly as it fades; on the 2D tree the fall is one Web Animation pinned to its start (tree.js playLeafFall), so a refresh mid-fall does not restart it. The admin's Display 2D/3D Tree (treeParameters.treeDisplayMode) chooses the tree on the wall: /tree and /3dTree both open the chosen tree (the other address redirects, keeping any ?options; backend/features/parameters/treeDisplay.js, on both servers), and an open tree page switches by itself within about 5 seconds of a change (not the admin's /tree-demo). The 2D tree's picture style (treeParameters.treeStyle, "Tree picture style" in the admin's 2D Tree Display, checklist item 12) is Painted (the original stage pictures, the default), Natural (the 3D tree in daylight) or Digital (the glowing 3D tree): Natural and Digital show a picture of the 3D tree itself at the current growth stage, in its river valley, covering the screen, so the 2D and 3D screens match, and the visitors' 2D leaves sit on its canopy (tree.js loadTreeImage, tree.css body.tree-from-3d). For each style and stage, assets/Tree/2d-from-3d/<style>/ keeps stage<N>.jpg (1920 x 1080), stage<N>-canopy.png (opaque where the tree's foliage is, measured but never shown: where the leaves may sit) and stage<N>.json (when it was captured, the canopy's box, used as the leaf area if no spot is found, and the tree's foot). The 3D page makes them itself: /3dTree/3dTree.html?capture2d=1&look=natural|glow&stage=N&growth=1 shows the tree still from the front, a little further out than the standard view (CAPTURE_ZOOM), in clear weather with the river at its normal level, without the visitors' leaves, birds or falling leaves, and stays on the 3D tree even while the wall shows the 2D tree; window.tree2dCapture() draws the frame and finds the canopy by drawing it again without the tree's foliage (frontend/3dTree/capture-2d.js). The admin's "Capture from the 3D tree" button runs this for both styles and all five stages in a small window (about 2 to 4 minutes, with Stop) and saves each picture through POST /api/admin/parameters/tree-style-capture (admin only; backend/features/parameters/tree2dStyle.js checks the style, the stage, that the pictures are a JPEG and a PNG within size, and keeps only the numbers of the description); node scripts/tree/capture-2d-from-3d.js does the same without the admin page (the server running). Capture again after changing the 3D tree (for example its trunk glow). A stage not captured yet shows the painted tree, and the admin's thumbnails say "Not captured yet"; Save Display warns about it. The pictures are wide panoramas (3840 x 1080, 32:9, about the ESG Centre wall's 7:2): the tree framed as for a 16:9 picture (CAPTURE_FRAMING_ASPECT), the sides showing more of the valley. Both trees fit any screen, from a 16:9 screen of any size to the 7 m x 2 m wall or an upright one: on the 2D tree the view designed for a 1917 x 1007 screen (DESIGN_SCREEN in tree.js) is scaled to fit inside the screen, centred (tree.js layoutTreePictures; the painted tree's 2200 px width scales with it, and a captured panorama shows its middle 16:9 on a 16:9 screen and more of its sides on a wider one), the leaves, their names, the leaf area, the title box and the Year Review button scaling with it (screenScale, --tree-screen-scale; the title box and button never below 60%), and any room a captured picture leaves is filled with a soft blurred copy of it (tree.css body.tree-from-3d::before); the 3D tree's camera already keeps the whole tree in view on any screen (tree-view.js frameHeight and frameWidth), a wider screen showing more of the valley, and its title card, Year Review and credit scale with the screen (scene.js --screen-scale). Checked in Chrome at 1917 x 1007, 3500 x 1000 and 1920 x 549 (7:2), 1280 x 1024 and 1080 x 1920: the whole tree and every leaf on screen at each. Each tree also has a Screen size setting for a display fed a picture of another shape (as an LED wall's controller often is): 2D Tree Display > Screen size (treeParameters.screenSize, saved with Save Display) and 3D Scene Controls > Screen size (tree3dParameters.screenSize), each { preset, width, height }: Auto (fit the screen, the default), a preset (ESG Centre LED wall 7 m x 2 m, 16:9, 21:9, 32:9, 4:3, upright 9:16) or Custom, a width and height in any unit (7 and 2 metres, or 3840 and 1080 pixels); only the shape matters, and the admin sees it ("Shape 3.50 : 1, wider than 16:9"). The server checks it (backend/features/parameters/screenSize.js: positive numbers, at most 100000, no thinner than 1:10) and fills in a preset's size. With a shape set, the whole tree page (2D: #treeContainer, tree.js applyScreenShape, with the tree's background, title box, Year Review and details card inside it; 3D: .reserve, frontend/3dTree/screen-shape.js, the scene framing the tree for that shape itself) is drawn in that shape, as large as the window allows, centred, black round it, and again when the window changes size. The 3D page is the self-contained Ketapang River scene (frontend/3dTree/3dTree.html with scene.js and its modules, three.js bundled in vendor/, models and audio in assets/); see frontend/3dTree/README.md. The admin's 3D Tree Settings tab sets the 3D page's weather, rain area, river level, sound (if the browser waits for a first touch, the 3D page says "Tap anywhere to turn on the sound" and any touch starts it; Listen here plays the river and bird sounds in the admin), the automatic turn (on or off, one full turn every 30 seconds to 24 hours, to the right or left: autoOrbit, orbitSeconds, orbitDirection), sound (ambient sounds the admin picks, each with its own tickbox and volume: River water, Birds and Forest wind on, Gentle rain and Night insects off, ambientRiver and so on with …Volume, frontend/3dTree/ambience.js; and a background music in the admin's style, Calm kalimba, Soft piano, Dreamy pads or Music box, all composed live by the page, or My uploaded music (the admin's own music file, uploaded to assets/Tree/music and played looped: musicStyle uploaded, musicTrack; /api/admin/parameters/tree3d-music/upload, list and delete), or None, frontend/3dTree/background-music.js: musicStyle, musicEnabled, musicVolume; the admin's Listen here plays the screen's own sound engine), soil cutaway, which on-screen panels show, and its title box (the same settings as the 2D title box); they are saved as `tree3dParameters` through PUT /api/admin/parameters/tree3dParameters and the 3D page (tree3d-settings.js) applies them from /api/parameters within about 5 seconds. Its 3D Leaf Adjustments set the feedback leaves on the 3D tree (frontend/3dTree/feedback-leaves.js, the RainTree leaf model in assets/Tree/3dTreeLeaves): new and older leaf colours, the names' font style, weight, colour and size (leafNameFont, leafNameWeight, leafNameColor, leafNameSize 0.7 to 1.4; Names on the leaves, with a preview), how long a leaf counts as new, leaf scale (how many leaves: the same as the 2D tree, its Maximum Visible Leaves and growth stage); there is no leaf upload for 3D. Its 3D VIP Leaf Adjustments set the gold VIP leaves (VIPs are the names in VIP Management): their gold, scale and gold glow, and the VIP names' own style when "Give VIP names their own style" is ticked (vipNameOwnStyle, vipNameFont, vipNameWeight, vipNameColor, vipNameSize: font style, weight, size 0.7 to 1.4 and colour, with a preview on the gold leaf; off by default, so VIP names are written as the others). Its 3D Tree Visualization Parameters are the 2D Visualization Parameters for the 3D tree (leaf area, refresh interval, opacity, appear, float-up time, fall duration, badge leaf colours; the bottom-middle time is the 2D tree's, shared by both trees; saved in tree3dParameters), with Maximum Visible Leaves shared with the 2D tree (treeParameters.leafFallThreshold, now also accepted by PUT /api/admin/parameters/treeParameters). Maximum Visible Leaves is first in, first out on both trees, the new leaf first: the oldest leaf stays until a new leaf has floated up and joined the tree, then falls, one for each new leaf (3D: feedback-leaves.js fallQueue, letOldestFall; 2D: tree.js getLeafCycleState holds the oldest leaves while new ones wait at the bottom middle or fly up, releaseHeldLeafFalls lets one go as each lands; with no new leaf coming, as when the admin lowers Maximum Visible Leaves, the extra leaves fall at once); the 3D tree makes many leaves smaller so they fit. A 3D leaf joins light and turns dark after its light period (tree3dParameters.leafNewHours, minutes or hours; the dark shade may go down to OLD_MIN_LIGHTNESS in feedback-leaves.js, so it reads clearly as a dark shade): light to dark green, or (by default) a light to a dark shade of its badge colour, the 3D badge colour once changed in the 3D panel and otherwise the 2D tree's badgeLeafStyles colour. Every 2D leaf (not a VIP's) is likewise its badge's colour from Badge Leaf Styling: a light shade for its first tint window (badgeLeafStyles.tintDurationHours, "A leaf stays light for" in Badge Leaf Styling, minutes or hours, stored to 3 decimals of an hour so 1 minute can be set; 24 hours when 0 or unset), then fades smoothly into the dark shade over 10 seconds (TINT_FADE_MS, playLeafTintFade in tree.js, timed by the clock so the leaves rebuilt at each refresh carry on the fade), then a darker shade (tree.js adds .leaf-tint-aged; tree.css). The 3D tree grows through the same stages 0 to 4 as the 2D tree (the same treeStage, also settable in the admin's 3D Tree Growth Stage panel), showing the Ketapang_Stage_0 to 4 models in assets/Tree/3dTreeLeaves (frontend/3dTree/tree-stage.js), each with its trunk made round as it loads, so the trunk is as thick from the front and back as from the side (the models' trunks are oval, stage 4's 1.3 m by 2 m; roundTrunk), and its canopy shaped to look right from the side as the view turns (frontend/3dTree/canopy-shape.js: fewer leaves in the canopy's middle from front to back and deep inside, so the trunk and branches show from the side; the low-hanging underside trimmed, higher under the canopy's two long ends, so from the side the crown ends tidily above the trunk instead of hanging towards the ground; more on the outside of its front and back, so the outline from the side is full on both sides and the feedback leaves there sit among leaves); the /3dTree page changes to a new stage in place, without reloading (the tree grows into it). In Auto (treeParameters.treeStageMode 'auto', saved by either admin panel) the stage grows by itself: GET /api/parameters reports the stage for this year's leaf count and the leafThresholds (backend/features/parameters/treeStage.js, with the count from features/tree/routes.js countLiveTreeLeaves), so both trees move up within about 15 seconds of reaching a threshold; Manual keeps the chosen stage, shown full. Between the stages the 3D tree grows a little with every leaf: /api/parameters also reports how far the tree is from this stage's threshold to the next (treeStageAuto.progress, stageProgress in treeStage.js), and the tree's own foliage fills in with it, slowly (about 9 seconds per new leaf, without a reload), from the middle of the canopy outwards, the new growth a fresh lime green at the leaf's own brightness (never glowing at night) fading into the canopy over about 20 seconds, until the canopy is full at the next stage's threshold; nothing already grown is taken away and the visitors' leaves stay; on reaching a new stage the tree grows into it in place, without reloading the page: the new stage's model loads in the background, takes the tree's place at the same size with the foliage it had, then grows to its own size with a growth spurt of fresh foliage; the visitors' leaves move with it: each goes to the same part of the new canopy (high on the left stays high on the left), onto its foliage, gliding there over about 3 seconds, then grows out with its branch as the tree grows to its new size; a leaf floating up at the time glides on to its new spot; the first leaves after a fresh start (the tree still a bare Stage 0 trunk) wait for the Stage 1 tree and then show in the row and float up as usual; going down to Stage 0 the leaves fall off, and they fade back onto the canopy of the next stage up (frontend/3dTree/feedback-leaves.js moveLeavesTo, followTree, waiting); it is fully grown at the Stage 4 (Full Canopy) threshold, set in the admin (frontend/3dTree/tree-growth.js). The admin's 3D Tree Growth Stage panel shows how far it has grown ("60% grown towards Stage 3 (6 more leaves)"). ?stage=2&growth=0.5 on /3dTree shows a stage part grown, ?stage=3&growFrom=2 stage 3 just reached, with its growth spurt. In the natural look the 3D tree is shaded for the time of day like the rest of the scene (cool moonlight at night, warmer at dusk; frontend/3dTree/matte-tree.js), the feedback leaves a little less so they stay readable. The 3D page has the glowing look of the ESG Centre's concept (frontend/3dTree/glow-look.js): the scene at night, light streams running along all the wood (the trunk, every branch and the roots), each a bright line in a soft halo of its colour, which the admin turns on or off and makes thinner or thicker and brighter (3D Scene Controls > Look: "Trunk glow", tree3dParameters.trunkGlow, and its Strength, trunkGlowStrength, 50 to 200%; off shows the plain bark in the moonlight), the tree's own leaves glowing, each leaf green, blue or orange (Environmental, Social, Governance), rings of light round the base (no floating specks of light), all in those three colours, with the light of the leaves, light streams and rings spilling round them (a bloom: glow-look.js createBloom, the things on GLOW_LAYER drawn again small, blurred and added onto the frame). The admin's 3D Tree Settings has a "Glowing look" switch (tree3dParameters.glowLook, on by default, checked in backend/features/parameters/tree3d.js); off shows the daylight river valley with natural leaves, and an open 3D page reloads into the chosen look within about 5 seconds (?look=natural or ?look=glow fixes one). The 3D feedback leaves glow like leaves of light (in both looks in the admin's colour for the visitor's badge, as the 2D tree: Ocean Guardian blue, Climate Champion teal, Social Champion amber and so on, light while new and a dark shade later (3D Scene Controls: Colour leaves by their badge, badgeLeafColors); with that off, in the glowing look green, blue or orange by the badge's E, S or G, ESG_GLOW_COLOURS in feedback-leaves.js; glowing veins and an outline in the leaf's own colour, not white, a soft breathing glow in its colour and an occasional light sweep); a VIP's gold leaf has a star of light twinkling at its tip in both looks (LEAF_TIP, SPARKLE_SIZE; the admin can turn it off: 3D VIP Leaf Adjustments, "White star twinkling at the tip of VIP leaves", tree3dParameters.vipSparkle, on by default), and on the tree it turns gently from left to right and back on its stem, 40 degrees each way every 6 seconds, so its name stays readable (VIP_TURN_ANGLE, VIP_TURN_SECONDS; the admin can turn it off: "VIP leaves turn gently from left to right", tree3dParameters.vipTurn, on by default), with the visitor's name in white handwriting (frontend/3dTree/feedback-leaves.js GLOW_FRAGMENT). Clicking a 3D feedback leaf opens the same leaf detail card as the 2D tree (name, privacy label, badge, date, pledge snippet; frontend/3dTree/leaf-detail.js), beside the leaf. On both trees the card opens beside the clicked leaf (on the side with more room, kept on screen) and closes with its button, Escape, a click away from the leaves, or when the leaf falls; on the 3D tree it also closes as soon as the view is turned (feedback-leaves.js). On both trees feedback leaves stay clear of the title box wherever the admin positions it: new leaves are never placed under it, the bottom-middle start rises above a bottom title box, and leaves it covers after it moves or resizes are given new spots (2D: tree.js getTitleKeepOut; 3D: feedback-leaves.js titleArea and keepClearOfTitle). The 3D view shows the admin's chosen view: in the 3D View & Zoom card the admin turns and zooms a live preview (3dTree.html?viewEditor=1, 0.5 to 2.5 times the standard framing), saves views as named snapshots (tree3dParameters.savedViews, up to 12) and chooses the one the screens use (screenView; frontend/3dTree/view-settings.js, tree-view.js); viewers cannot zoom; when the tree turns (the automatic turn, dragging or the arrow keys), the feedback leaves stay on the side facing the viewer and glide smoothly with the tree, facing the viewer; a leaf stays fully shown all the way to the side of the tree's outline and goes out of sight only there, quickly, coming back in on the other side; leaves that would cover each other as the viewer sees them (two at different depths lining up as the tree turns) are eased apart across the view, keeping to the canopy, and settle back when the view moves on (feedback-leaves.js spreadApart); a VIP's leaf always joins the tree at one end of the canopy, its left or right as the viewer sees it, and a leaf made VIP on the tree moves there (feedback-leaves.js sideSpots), then glides with the tree like the others, so the front always has its leaves (feedback-leaves.js shownSpot, GLIDE_REACH).

Role 3 hooks (Visitor Data Archive, marked in routes.js, tree.js and 3dTree.js). See docs/features/archive.md.

- Leaves stay after an archive. When the Visitor Data Archive deletes a visitor's records, their leaf stays on the tree (the admin setting "Leaves on the tree": keep without a name, keep with initials, or remove). GET /api/tree, with or without `year`, returns the kept leaves of that year from the table archived_leaves together with the live rows, in the same order (created_at, then id). A kept leaf has the same fields as a live row plus `archived: true`: `id` is the old feedback id, `name` is the label ("Visitor" or initials such as "J. T."), `badgeKey`, `badgeName`, `badgeColor` and `isVip` are as they were, `pledgeSnippet` and `pledgeTopic` are empty, `visit_count` is 1, `user_created_at` is null and `privacyLabel` is "Details archived". The pages draw it like any other leaf; its detail card shows the label, the badge, the month and year of the visit and "This visitor's details were archived." (the one marked block in openLeafDetail of tree.js and 3dTree.js). The leaf keeps its key, so it never plays the landing animation again, but its spot changes once, because getVisitorSeed uses the name.
- Year book. GET /api/tree/years counts kept leaves as leaves of their year (`keptLeafCount` says how many) and adds the leaves that are really gone to leafCount as before (`archivedLeafCount`); the book shows "N leaves · M archived", where M is only the leaves that are gone.
- If archived_leaves cannot be read (the migration has not run yet), both routes answer with the database rows only and the server log says to run npm run db:migrate.

**Known issues (from the October 2026 review, line numbers refer to the layout before the restructure where noted)**

- Live tree polls every 5 s regardless of leafRefreshInterval, 4 requests and a full rebuild each time (tree.js 2042).
- Auto growth stage is computed once when the admin saves; nothing re-evaluates it as leaves arrive (the thresholds are stored and reloaded into the form since 31 Oct).
- Empty number boxes save 0 and the wall uses hidden defaults (admin/js/parameters.js + tree.js 411).
- Tree keeps archived rows that pulse and pledgeboard hide (treeRoutes 112).
- Default background path wrong in parameters/store.js 185 (black wall on a fresh install).
- Fixed 18 Nov 2026: the badge tint duration had no admin input (param-tintDurationHours), so it was always 0 (24 hours); it is now "A leaf stays light for" (minutes or hours) in Badge Leaf Styling.
